MovieMotions · Retrieval

The full retrieval pipeline

Five stages. Each one receives something, does one job, and passes something on. Read the coloured tag on each box: gate, retrieve, fuse, reorder, return.

User query

"something with creatures chasing you, Denzel, under 2 hours"
Stage 0 · Parse

Split the query into two kinds of thing

An LLM reads the sentence and separates the hard constraints (facts that are non-negotiable) from the soft meaning (the mood to search on). This is the query-parsing step — extraction, not inference.

hard → { actor: "Denzel Washington", max_runtime: 120 }
soft → "creatures chasing you, intense"
the hard facts become a filter ↓    the soft text becomes the search ↓
Stage 1 · Metadata filter — THE GATE

Throw out everything that breaks a hard rule, before searching

A plain SQL WHERE. No Denzel? Over 2 hours? Gone — never even considered. This shrinks 20 films (later: thousands) down to only the eligible ones. Runs first because a hard constraint is a guarantee, and because searching a smaller set is faster and more accurate.

candidate set = films WHERE 'Denzel Washington' = ANY(cast)
                 AND runtime_minutes <= 120
Why the gate is first, not last. Filtering after ranking wastes work ranking films you'll only delete — and risks the top 3 being all ineligible. Enforce the non-negotiables, then rank what survives.
Stage 1b · Knowledge graph — A SMARTER GATE

Filter by relationships, not just attributes

The metadata gate asks "does this film have property X?" The graph asks "do two entities relate the way the query needs?" It stores typed edges between things — a creature that hunts a human is a different edge from a creature that is a pet. Same position as Stage 1 (a gate that narrows), more expressive power (relationships, not flat facts).

query needs: creature —HUNTS→ human

Predator creature —HUNTS→ human ✓ keep
Jurassic Park creature —HUNTS→ human ✓ keep
Alien creature —HUNTS→ human ✓ keep
The Hangover tiger —IS_PET→ (comedy) ✗ DROP
This is the tiger fix. "Creatures chasing you" wrongly returned The Hangover because its blurb says "a tiger in the bathroom" — the vector knew a creature was mentioned but not its role. The graph drops it here, at the gate, so it never even reaches the searches below. A vector matches entities that are mentioned; a graph matches entities that relate the same way.
The candidate set — "the arena"

{ Predator, Jurassic Park, Alien }

This narrowed set is what stays fixed while the two searches run. The graph drew these walls; both searches below operate only inside them. The graph's job is done — it does not rank, and it does not enter the fusion.

Stage 2a · Vector search

Match by meaning

Embed the soft text into a vector, compare with cosine against the candidate films' vectors. Links "creatures" to "dinosaur" even though the words differ.

list A (ranked):
1 Predator
2 Jurassic Park
3 Alien
Stage 2b · Keyword / BM25

Match by literal words

Scores how well the query's actual words hit the same content text — no embedding. Catches exact names and terms a vector blurs. (Little to bite on at 20 blurbs; earns its keep with reviews.)

list B (ranked):
1 Alien
2 Predator
3 Get Out
The two lists' scores are NOT comparable. Cosine ~0.6 and a BM25 score of 14.2 live on different scales — exactly the finding from space_shape.py. That is why the next stage fuses on rank, not score.
Stage 3 · Reciprocal Rank Fusion

Merge the two lists into one — using position, not score

Throw the scores away. Keep only where each film ranked in each list. A film scores 1/(60 + rank) for every list it appears in; add those up; re-sort. A film that both methods liked rises; a film only one liked still gets a fair shot. Dedupe to one row per film here.

Predator: 1/(60+1) + 1/(60+2) = 0.0325 → #1
Alien   : 1/(60+3) + 1/(60+1) = 0.0323 → #2
fused list → top 10 kept
RRF fuses the two RETRIEVERS — not the graph. Vector and BM25 each produced a ranked list, so there are two scorecards to merge. The graph produced no scorecard; it set the boundary. So the count is: one filter (graph) → two searches fused (vector + BM25) → one list. RRF needs two lists to exist, which is why it can't run in your system yet — you have only the vector lane today.
top 10 candidates ↓ (small enough to afford the expensive step)
Stage 4 · Reranker

Re-read query + each film together, and reorder

Stages 2–3 compared two things made separately. A reranker (cross-encoder) reads the query and one film's text at the same time and asks "is THIS actually about creatures chasing you?" — the only genuinely trustworthy relevance score in the pipeline. Costly, so it runs on just the top 10, never the whole corpus.

reorders the 10 → Predator, Jurassic Park, Alien, …
This is the one that fixes your 1/3 problem. Jurassic Park and Alien, buried by the mood chunks, get re-read against the query and pulled back up. Reranking needs no second list — which is why it's the first thing to build.
Stage 5 · Return

Top 3 to the user

Predator · Jurassic Park · Alien
How the three relate — together, alone, or in pairs?

The graph works ALONE, and first. It's a filter. It narrows 20 films to an eligible set and then steps back. It does not rank, and it does not fuse. (Its output is a set, not a list.)

Vector and BM25 work as a PAIR. Both search the same narrowed set, each producing a ranked list — one by meaning, one by literal words.

RRF fuses that pair — two lists, not three. The graph isn't in the fusion because it never made a scorecard. So the shape is: 1 filter → 2 searches → fuse the 2 → rerank → return.

Advanced footnote (GraphRAG): you can also let the graph retrieve — walk from the Denzel node to his films to similar themes — which makes it a third ranked list, and then RRF fuses all three. But that's the graph doing a second, harder job. Its clean primary role, the one that matches "a graph is a filter, not a ranker," is the gate above.
Where MovieMotions actually is right now.

Stage 1b knowledge graph — not built (overkill at 20 films; a real point at scale)
Stage 2a vector — built
Stage 2b BM25 — not built
Stage 3 RRF — not built (nothing to fuse until 2b exists)
